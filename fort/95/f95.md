# F95 auto deallocation
- Fortran 90 introduced the allocatable array

	
	`...`
	`! specify that an array "x_ray" is allocatable`
        `real, allocatable :: x_ray(:)`
	`...`
	`...`
	`! allocate memory for the array`
        `allocate(x_ray(10))`
	`! use it`
        `do i=1,10`
                `x_ray(i)=i+2`
        `end do`
	`! deallocate the array`
        `deallocate(x_ray)`

	
	
- After an array is deallocated it can not be used (until reallocated)
- If an array is in a subroutine and the subroutine returns the status of the array is unknown
- This is a portability issue, different compilers can do things differently
- Program correctness?
- Memory leak

# F95 auto deallocation
 In F95 and beyond if an array is allocated in a subroutine it is automatically deallocated on exit
- Prevents memory leaks
- Programs compiled under F90/F95 might behave differently 
- Related: Pointers in F90

A pointer is a variable that can be used in place of a regular variable or an array. The variable that is being pointed to must be given the target attribute. We will use a pointer to illustrate the differences in allocatable arrays in F90/F95

# F95 auto deallocation - Our example
The following program is, at best very poorly written.  We'll see that its output is dependent on the compiler used and compile time options. 

In our example we have: 
- A pointer, vector, that is "global" defined in a module
- Subroutine "dummy"
  - Checks the status of vector and x_ray
  - Allocates and fills a local x_ray "x_ray"
  - Points vector to dummy
  - Uses the ASSOCIATED function to show the status of x_ray and vector
  - Dummy does not deallocate the array
- Our main program calls dummy twice and does <b>illegal</b> references to "vector"


#### Source: - [test1.f90](https://github.com/timkphd/examples/blob/master/fort/95/test1.f90)


```

 2         integer, POINTER, DIMENSION(:) :: VECTOR 
 3 end module
 4 subroutine dummy(i,k)
 5         use aptr
 6         !save
 7         integer, allocatable,target :: x_ray(:)
 8         write(*,*)"in subroutine....call ",k
 9         write(*,*)"vector associated", ASSOCIATED(vector)
10         write(*,*)"x_ray allocated ",allocated(x_ray)
11         write(*,*)"vector ",VECTOR
12         !write(*,*)"x_ray  ",x_ray
13         if(.not. allocated(x_ray))allocate(x_ray(i))
14         x_ray=-1
15         do j=1,i
16           x_ray(j)=j
17         enddo
18         write(*,*)"vector associated", ASSOCIATED(vector), &
19                   " vector points to x_ray",ASSOCIATED(vector,x_ray)
20         vector=>x_ray
21         write(*,*)"vector associated", ASSOCIATED(vector), &
22                   " vector points to x_ray",ASSOCIATED(vector,x_ray)
23         write(*,*)"sum(vector)",sum(vector),ASSOCIATED(vector)
24         write(*,*)
25 end subroutine
26 program xyz
27         use aptr
28         write(*,*)"in main before call to subroutine"
29         nullify(VECTOR)
30         if(associated(vector)) then
31                 write(*,*)"s0 sum(vector)",sum(vector),ASSOCIATED(vector)
32                 write(*,*)"v0",vector
33         else
34                 write(*,*)"vector not ASSOCIATED"
35         endif
36         call dummy(5,1)
37         write(*,*)"back in main after first call to subroutine"
38         if(associated(vector)) then
39                 write(*,*)"s1 sum(vector)",sum(vector),ASSOCIATED(vector)
40                 write(*,*)"v1",vector
41         else
42                 write(*,*)"vector not ASSOCIATED"
43         endif
44         call dummy(4,2)
45         write(*,*)"back in main after second call to subroutine"
46         if(ASSOCIATED(vector)) then
47                 write(*,*)"s2 sum(vector)",sum(vector),ASSOCIATED(vector)

49         else

51         endif
```

We compile and run with 4 different compilers.  The first set of compiles/runs we don't provide any command line options.  

Column 3 of our table is referencing the writes on lines 31 and 32.  The gnu and AMD print garbage on these lines while the other two print what looks like reasonable values.  Which is correct?  Neither.  But If I had to choose I would say the "garbage" output is better because it points to a "programmer error".  

The program is being compiled with Fortran 95 semantics.  x_ray is deallocated on the subroutine exit.  Because vector is in the module and the module never goes out of scope it is still associated.  However, vector points to an invalid memory location.  We got "reasonable" values is pure luck.  

In the second set of runs we compile with flags which "force" a save at the end of every subroutine.  In this case all the programs all produce the same values, which you might say are correct.  Unfortunately, the compilers are no longer compliant with the standard.  The compilers have masked problems with the program.  

This program can be "fixed", be compliant and thus be portable.  Uncommented the save on line 6 will cause all of the variables defined in the subroutine to maintain their status and values between calls.  

Recommendations:
* Put save in routines where you know you was preservation between calls.
* Do not use command line options to force saves except:
* Compile with and without the command line options and check if the results are the same.  
* For clarity explicitly deallocate before subroutine returns

# Stream IO
Fortran supports unformatted reads and writes.  Data is written as a collection of "machine native" bytes and is not normally intended for human readability.  There are severl reasons for unformatted IO.  

Unformatted IO:
- Is normally much faster
- Often more compact
- Maintains precision of values

Unformatted I/O are not new.  However there is a new mode called Stream. Stream output produces clean output.  What? Without Stream output every write adds beginning/end of record marks.  These are extra characters that other programs might not be able to handle. StreamI/O is similar to C binary write/read commands.  It only writes/reads values you want without "extras". This makes it easier to interact with other Fortran programs and even other languages.

# Diversion - linux od command

We're going to look at the linux command `od`.  It will be useful for seeing what unformatted IO in Fortran produces.  From the od man page we get: "od == Octal Dump, Write an unambiguous representation, octal bytes by default, of FILE to standard output."  So od takes a file and writes it out, by default, in octal (base 8) representation.  Fortunately there are many more options beside just writing in octal.  Here is a "simple" command with an explanation of the various options

`od -A d -j4 -v -N 64 -t f4 fort.10`

 * Write a file "fort.10" to the terminal
 *  -A d  =  header for the number the bytes written with decimal numbers (this is the left most column)
 * -j 4  = skip the first 4 bytes
 * -v    = don't skip repeats
 * -N 64 = write 64 bytes
 * -t f4 = format the output as 8 bytes reals


Other formats include: 
- -c    = write as characters
- -b    = write as octal bytes
- -t f4 = format the output as 4 bytes reals
- -t d# = write as integers of size #

# A bigger Fortran example

#### Source: - [bin.f90](https://github.com/timkphd/examples/blob/master/fort/95/bin.f90)
- The program [bin.f90](https://github.com/timkphd/examples/blob/master/fort/95/bin.f90) reads from the command line what type of data to write in 32 byte blocks
        
  - "i2" - 16 2 byte integers
  - "i4" -  8 4 byte integers
  - "i8" -  4 8 byte integers
  - "x4" -  8 4 byte reals
  - "x8" -  4 8 byte reals
  - "c1" -  (/"1","2","3","4","5","6","7","8"/) 4 times
  - "c8" -  "!@#$%^&*" 4 times
  - "cx" -  "abcdefghABCDEFGH" 4 times
  - "st" -  stop input

* It opens two unformatted files without access=stream with access=stream
  * open(unit=9, file="fort.9", form="unformatted",status="replace")
  * open(unit=10,file="fort.10",form="unformatted",status="replace",access="stream")
* Writes the data
* Closes the files
* Reopens the files and reads the data back
* Calls a function to return the length of each file.  For this version of the program we get the length by opening the file and read/count character by character

# F2003 Fortran and C interoperability
<dl>
	<dt>This section "borrows" heavily from: </dt>
		<dd><a href="https://gcc.gnu.org/onlinedocs/gfortran/Interoperability-with-C.html">https://gcc.gnu.org/onlinedocs/gfortran/Interoperability-with-C.html</a>.</dd>
</dl>

People have been writing mixed language programs for years.  Many libraries called from Fortran are written in C, for exmple MPI.  Many libraries called from C are written in Fortran.  There are issues:

 * How do you handle things like derived typed and global variables?
 * Fortran (usually) does a call by reference C does a call by value.
 * There has not been a standard way to do this.
        
    



Since Fortran 2003 (ISO/IEC 1539-1:2004(E)) there is a standardized way to generate procedure and derived-type declarations and global variables which are interoperable with C (ISO/IEC 9899:1999).  Fortran 2003 adds a data type attribute <b>bind(c)</b>, and a module, <b>ISO_C_BINDING</b> which standardizes Fortran/C ISO_C_BINDING.
- ISO_C_BINDING contains:
    - 6 intrinsic procedures
    - Over 20 Fortran data types that map to C types
    - 8 Character constants
    - 2 Null pointer types

# ISO_C_BINDING intrinsic procedures

* C_ASSOCIATED - Status of a C pointer
  * C_ASSOCIATED(c_ptr_1[, c_ptr_2]) determines the status of the C pointer c_ptr_1 or if c_ptr_1 is associated with the target c_ptr_2.
* C_F_POINTER - Convert C into Fortran pointer
  * C_F_POINTER(CPTR, FPTR[, SHAPE]) assigns the target of the C pointer CPTR to the Fortran pointer FPTR and specifies its shape.
* C_F_PROCPOINTER - convert C into Fortran procedure pointer
  * C_F_PROCPOINTER(CPTR, FPTR) Assign the target of the C function pointer CPTR to the Fortran procedure pointer FPTR.
* C_FUNLOC - Obtain the C address of a procedure
  * C_FUNLOC(x) determines the C address of the argument.
* C_LOC - Obtain the C address of an object
  * C_LOC(X) determines the C address of the argument.
* C_SIZEOF - Size in bytes of an expression
  * C_SIZEOF(X) calculates the number of bytes of storage the expression X occupies.

Our Function getlen_c replaces getlen in our previous program.  It takes a file name and returns a file length.

```    
    module getit
    contains
    function getlen_c(fname)
        USE ISO_C_BINDING, ONLY: c_long, c_char,C_NULL_CHAR
        use numz
        integer(in8) :: getlen_c
        interface 
            integer(c_long) function filesize(aname) BIND(C, NAME='c_filesize')
              USE ISO_C_BINDING, ONLY: c_long, c_char
              character(kind=c_char) :: aname(*)
            end function fileSize
        end interface
        character(*) :: fname
        character(128) :: tmp
        character(kind=c_char) :: string(128)
        integer strlen
        ! fill the string with nulls (strings for c must be null terminated)
        string=C_NULL_CHAR
        ! copy our input string to a c_char string
        tmp=trim(ADJUSTL(fname))
        strlen=len_trim(tmp)
        do i=1,strlen
            string(i:i)=tmp(i:i)
        enddo
        getlen_c=fileSize(string)
    end function
    end module
```    



ISO_C_BINDING contains our Fortran equivalent data types.  Here we are going to define variables that have typed matching C long and C char.  We are also going to use the C null character.

Our function returns an integer of type "in8".  In8 is defined in "numz" to be an 8 byte integer.

Next we have the interface for our C routine.  It will return a C long and take a C character array.  

The BIND clause first "just" says that this is a C routine.  If you have ever written mixed language programs you will appreciate the NAME='c_filesize' clause.  What this does is specify the name of the routine in C.  Why is this important.  Previously, if you wrote a mixed language program the Fortran compiler may or may not append and underscore (_) to the end of the routine name.  So on the C side you would need to be able to compile with or without the underscore.  Here we are forcing the Fortran compiler to name our C function as given.

The string we are sending to the C routine is defined next.  We are going to fill it with NULLs.  This is a bit of an overkill.  Only the character after our filename needs to be NULL.Next we "unpad" our input string and copy it to our C string. Finally we call the C routine.

# Object-oriented programming (OOP) in Fortran...

### object-oriented programming...

- You can define classes that contain both data and methods which operate on that data

- Then create separate instances of the class, each with its own data methods called from an instance of the class will work on its data


### Fortran Support in 33 seconds or less

- Fortran 90 modules may contain data, but there is no notion of separate instances of a module.

- A Fortran 90/95 module can be viewed as an object because it can encapsulate both data and procedures. 

- Fortran 2003 (F2003) added the ability for a derived type to encapsulate procedures in addition to data. 

- F2003 also introduced type extension to its derived types which implements inheritance.

- Inheritance allows code reusability through an implied inheritance link in which leaf objects, known as children, reuse components from their parent and ancestor objects.

- Polymorphism is also supported in Fortran 2003.

- Polymorphism occurs when a procedure, such as a function or a subroutine, can take a variety of data types as arguments. 

- You can also have data polymorphism - a pointer can point to different data types
